# Research application

This note separates three layers.

- **Published findings** are results reported by the cited sources. This lab did not remeasure them.
- **Design hypotheses** are local choices about how to adapt a finding to a session-fee sheet. They are not theorems from the sources.
- **Local measurements** are outputs of this package's tests and of `run_controls()` on the synthetic fixtures. They are not a new scientific result.

The original contribution is the adaptation and the behavior the tests verify: declared units, a literal week total, a shallow staging formula, a pre-coercion operation fingerprint, and a validate-then-flush batch with a lock stub. No live Google API was called.

`portfolio_manifest.json` records `research_backed: true` and `reference_count: 10` for the ten sources below. Two catalogued sources were not used as evidence: the archived RFC 9110 extract does not contain the idempotent-method section that later commentary points at, and the JSON Schema draft was not in the readable archive.

## 1. Independent bottom-line oracle

**Source.** `panko-2016-spreadsheet-errors`. Raymond R. Panko, "What We Don't Know About Spreadsheet Errors Today." https://arxiv.org/abs/1602.02601 (EuSpRIG 2015 proceedings text). Abstract, page 1; Section 2.1, Tables 1 and 2, pages 2–4; Section 5, page 13.

**Published claim.** The abstract's first conclusion is that cell errors are uncommon one by one, while a large sheet is very likely to contain at least one wrong bottom-line value. Section 2.1 compiles a 3.9% cell error rate across 14 laboratory studies and 967 solo participants, and errors in 94% of 85 intensively inspected operational spreadsheets. Section 5 argues for much more testing and warns that an untested prescription can backfire; the strong-typing example there is that extra burden on an overloaded developer can create other errors. Those rates and that warning are Panko's. They are not an input to the checker and were not remeasured here.

**Adaptation.** A session row can satisfy type, sign, dimension, and `amount = hours * rate` while the stored week total is only the first row. `schema.py` is the per-cell check. `invariants.py` compares the stored total and row count with literals from the fixture file. It does not call `transform.group_total`. The fixture author states `15500` as `10000 + 3500 + 2000`.

**Code.** `src/sessionfee/schema.py`, `src/sessionfee/invariants.py`, `src/sessionfee/transform.py` (`first_row_only_total`, `dropping_total`, `group_total`), `examples/fixture_a_cell_valid_wrong_total.json`, `examples/fixture_b_non_numeric_amount.json`, `examples/fixture_c_shared_oracle.json`.

**Tests.** `test_fixture_a_schema_baseline_passes_and_invariant_fails`, `test_fixture_a_passes_dimensions_and_fails_invariant`, `test_fixture_b_schema_baseline_already_fails`, `test_fixture_c_shared_function_oracle_is_blind`, `test_invariant_checker_does_not_call_the_writer_total`, `test_commit_refuses_a_disagreeing_literal_total`, `test_measure_report_matches_the_direct_fixture_a_split`.

**Local measurement.** On fixture A, schema pass is true, schema failure count is 0, and invariant pass is false. The dimension check on those same rows is also true, so units do not detect the omitted rows. On fixture B, schema pass is false; the bad text cell is already visible to the baseline, and this case does not show an oracle benefit. On fixture C, the shared dropping function agrees with itself (pass true) and disagrees with the file literal `15500` (pass false). That is a negative result for an oracle that is not independent. `group_total` on the same three amounts does equal the hand sum; that confirms the literal, and it is not what `check_invariant` computes.

**Limitation.** The oracle helps only when someone can state the total without using the writer under test. It does not help when the only definition of the total is that writer, when the defect is a single illegal cell, or when there is no aggregate. A passing fixture is not evidence that operational spreadsheet error rates fell.

## 2. Declared dimension unification

**Sources.** `chambers-erwig-2008-dimension-inference`. Chris Chambers and Martin Erwig, "Dimension Inference in Spreadsheets." https://web.engr.oregonstate.edu/~erwig/papers/DimensionInference_VLHCC08.pdf (VL/HCC 2008). Introduction, page 1; Section 3, addition semantics and conversion factors; Section 6.2, page 6. Also Panko Section 5, cited above, for the cost of extra typing burden.

**Published claim.** Section 3 requires both arguments of addition to have the same dimension and leaves addition of different dimensions undefined. It also says a pure factor is not general enough for Fahrenheit-to-Celsius, and the authors kept the factor model because unification stays feasible. The introduction says type checking is limited and should complement testing rather than replace it. Section 6.2 reports header inference correct in 30 of 40 spreadsheets; the other 10 were repaired by hand before dimension inference. Manual review of the reported errors found three false positives from label analysis and, in that inspected set, zero false negatives. Fifteen of the 18 confirmed errors violated the addition rule. Header inference was the weak link. Those counts are their evaluation on a repaired subset. They are not acceptance numbers here.

**Adaptation.** This sheet's columns are owned by the lab, so each column has an explicit dimension: JPY, hour, JPY/hour, date, or dimensionless. Dimensionless is a real vector of no exponents, not a skipped check. Addition requires equal exponents and equal factors, so JPY does not add to a cent-scaled money value. Multiplication adds exponents. Hours times JPY/hour yields JPY. Header text is never parsed. Fahrenheit-to-Celsius raises `UnsupportedConversion`. Ordered comparison uses the same equal-dimension precondition as addition; that comparison rule is a **design hypothesis**, not a relational rule stated in Section 3.

**Code.** `src/sessionfee/dimensions.py` (`add`, `multiply`, `compare`, `dimension_for_column`, `fahrenheit_to_celsius`), `src/sessionfee/transform.py` (`session_amount`), `src/sessionfee/schema.py` (`dimensions_consistent`).

**Tests.** `test_jpy_plus_jpy_passes`, `test_jpy_plus_hours_numeric_baseline_accepts_and_dimension_rejects`, `test_hours_times_jpy_per_hour_yields_jpy`, `test_jpy_greater_than_hours_fails`, `test_dimensionless_plus_hours_fails_and_dimensionless_plus_itself_passes`, `test_header_amount_does_not_become_jpy`, `test_fahrenheit_offset_conversion_unsupported`, `test_different_money_factors_do_not_add`, `test_equal_factors_written_differently_still_add`, `test_jpy_times_jpy_is_not_rejected_by_the_factor_model`, `test_wrong_amount_dimension_fails_unification`, `test_fixture_a_passes_dimensions_and_fails_invariant`.

**Local measurement.** JPY + JPY passes. The numeric baseline accepts JPY 1000 plus 2 hours and returns `1002`. The dimension check rejects that pair. Hours times JPY/hour is labeled `JPY`. JPY > hours fails. Dimensionless + hours fails, and dimensionless + dimensionless passes. The header `Amount` is undeclared. Fahrenheit conversion is unsupported. Fixture A still passes dimensions while the invariant fails, which matches the paper's "complement, not replacement" point on this fixture and does not reproduce their detection counts. A negative local result: JPY times JPY is not rejected and is not equal to JPY. The factor model does not supply the paper's separate validity predicate, and this lab did not adopt one.

**Limitation.** A wrong rate that is still JPY/hour, a wrong total in one currency, and a sheet with no units all pass. Inferring units from headers was rejected because this schema is already declared and because their own evaluation called header inference the weak step.

## 3. Shallow staging formulas

**Source.** `hermans-2012-formula-understandability`. Felienne Hermans, Martin Pinzger, and Arie van Deursen, "Measuring Spreadsheet Formula Understandability." https://arxiv.org/abs/1209.3517 (EuSpRIG 2012). Abstract, page 1; Section 4.1, pages 4–5; Section 6.3.2.1, Table 3, page 10.

**Published claim.** The abstract says the number of ranges, nesting depth, and conditional operations make formulas harder to understand. Section 4.1 defines M1.1 as the number of direct references, M1.2 as the number of ranges those references are grouped into, M1.3 as the presence of conditional operations, M1.4 as parse-tree height, and M1.5 as calculation-chain length (cells traversed to the farthest referenced cell). Table 3, on 15 financial formulas judged by 40 professionals at one firm, shows M1.2, M1.3, and M1.4 correlating with perceived understanding and the ability to explain a formula. Nesting is the strongest of those (about -0.85 and -0.88 on the two understanding scores they mark at the 0.01 level). M1.1 does not correlate with those scores. M1.5 correlates with finding indirect references and, in their write-up, not with perceived understanding. They give no pass/fail cutoff. The sample is one company. This lab does not report a Spearman coefficient.

**Adaptation.** Fee rules stay in `transform.py`. The planner may emit only a staging formula. **Design hypothesis, local policy, not a Hermans cutoff:** height at most 2, at most one reference group, no conditional function (`IF`, `IFS`, `AND`, `OR`, `NOT`, `SWITCH`). M1.1 is recorded and does not decide acceptance. **Local operationalization of M1.5:** the number of formula cells on the longest formula-to-formula path, counting the start cell and not a trailing value cell. A chain of eight `=SUM(previous)` formulas measures 8. The local chain ceiling is 4. Python functions are outside the budget.

**Code.** `src/sessionfee/formula_budget.py`, `src/sessionfee/commit.py` (`staging_sum_formula` result `=SUM(F2:F4)`), `src/sessionfee/transform.py`.

**Tests.** `test_sum_one_range_passes_budget`, `test_if_fails_only_the_conditional_gate_when_it_has_one_reference`, `test_nested_conditional_example_fails_budget`, `test_two_ranges_fail_while_reference_count_is_not_the_gate`, `test_height_gate_rejects_a_triple_nested_sum`, `test_chain_of_eight_passes_per_formula_gate`, `test_local_chain_ceiling_of_4_rejects_eight_formula_chain`, `test_python_rule_is_outside_the_formula_budget`, `test_formula_budget_failure_makes_the_plan_apply_none`, `test_dry_run_does_not_mutate_and_logs_the_outcome`, `test_late_session_moves_the_formula_and_keeps_stored_amounts`.

**Local measurement.** `=SUM(A2:A10)` is accepted at height 1, one range, reference count 9. `=IF(A2,1,0)` fails only the conditional gate (height 1, one range). `=SUM(A2:A100)` has reference count 99 and is accepted. `=SUM(A2,B2)` has reference count 2 and is rejected for range count. The higher reference count passed and the lower one failed, which is why M1.1 is not the gate. `=SUM(SUM(SUM(A2)))` has height 3 and is rejected for height only. A chain of 8 formulas is per-formula-accepted, length 8, and fails the ceiling of 4. A chain of 4 is length 4 and passes that ceiling. The sheet form of the row rule, `=IF(D2>0,D2*E2,0)`, fails the conditional gate, while `transform.session_amount` returns JPY 10000 for 2.5 hours at 4000 JPY/hour. The staging formula always spans every stored amount; after a late single-session commit it becomes `=SUM(F2:F5)` one row lower, and the four stored amounts are unchanged. The per-formula budget alone does not see chain length; that is a limit of the three gates, and the separate ceiling is what makes the length visible. No user understood these formulas in a study here.

**Limitation.** Moving a single `SUM` of one range into Python would not make that formula easier under their metrics, and it would add a deployment boundary. Placement metrics (same column, reverse references) were weaker in their tables and are not a layout optimizer. If a later editor must change the fee rule inside the sheet, this split works against the people they measured.

## 4. Operation id and a pre-coercion fingerprint

**Sources.**

- `ietf-idempotency-key-07`. J. Jena and S. Dalal, "The Idempotency-Key HTTP Header Field", draft-ietf-httpapi-idempotency-key-header-07, 15 October 2025. https://datatracker.ietf.org/doc/html/draft-ietf-httpapi-idempotency-key-header-07 and the text form https://www.ietf.org/archive/id/draft-ietf-httpapi-idempotency-key-header-07.txt. Status of This Memo, page 1; Section 1, page 2; Section 2.2, page 3; Section 2.4, page 4; Sections 2.6 and 2.7, pages 5–6.
- `sheets-value-input-option`. https://developers.google.com/workspace/sheets/api/reference/rest/v4/ValueInputOption. Enums `RAW` and `USER_ENTERED`.
- `sheets-datetime-render-option`. https://developers.google.com/workspace/sheets/api/reference/rest/v4/DateTimeRenderOption. `SERIAL_NUMBER`.

**Published claim.** The draft's status section says Internet-Drafts are not to be cited except as work in progress, and this draft expires on 18 April 2026. Relative to 2026-10-07 that date has passed. Section 1, attributing the classification to RFC 9110, says POST and PATCH are not idempotent. Section 2.2 says the key must be unique and must not be reused with a different payload; a UUID is recommended. Section 2.4 says a fingerprint of the payload may be used and may be a checksum. Section 2.6 says a completed duplicate should return the stored result, and a retry while the first request is still in progress should conflict. Section 2.7 says a missing key on an operation that requires one should be rejected (they illustrate HTTP 400), a different payload should be rejected (they illustrate 422), and the in-progress retry should be rejected (they illustrate 409). Section 2.5.1 says a general client cannot assume the server honors the key. This lab implements the state machine locally. It does not claim the sheet speaks HTTP, and it does not claim conformance to a finished standard.

The ValueInputOption page says `RAW` stores values as entered and `USER_ENTERED` may convert strings to numbers, dates, or other types the way the Sheets UI would. The datetime page says serial numbers count days since 30 December 1899, with 1900-01-01 at noon equal to 2.5 and 1900-02-01 at 15:00 equal to 33.625, and that this treats 1900 as not a leap year.

**Adaptation.** Each session carries a client operation id. The fingerprint is SHA-256 of canonical JSON: sorted keys, stable decimal strings, ISO dates, and dimension tags, taken before the USER_ENTERED stub. Requiring the fingerprint is a local strengthening; the draft makes it optional. The stub rewrites an ISO date to a serial and is not Google's parser. Data cells in the plan use `RAW`. The staging formula uses `USER_ENTERED` and is not part of the fingerprint. HTTP status numbers are stored as comments on the outcome for the Apps Script example. Two different ids with the same business fields are two sessions. **Design hypothesis:** fingerprint-only deduplication would drop a legitimate second session, so it is the control, not the design.

**Code.** `src/sessionfee/canonical.py`, `src/sessionfee/coercion.py`, `src/sessionfee/idempotency.py`, `src/sessionfee/retry.py`, `src/sessionfee/dateserial.py`, `src/sessionfee/commit.py`.

**Tests.** `test_same_key_same_payload_one_row_and_append_baseline_two_rows`, `test_same_key_different_payload_conflicts_and_does_not_write`, `test_in_progress_conflict_does_not_write_until_completion_then_replays`, `test_missing_key_writes_nothing`, `test_two_keys_same_payload_two_rows_and_content_hash_drops_the_second`, `test_decimal_text_and_pre_coercion_fingerprint_are_stable` (including key-order independence), `test_user_entered_stub_changes_fingerprint_only_if_hashed_after`, `test_retry_backoff_replays_after_in_progress`, `test_raw_keeps_identifier_text_and_user_entered_stub_parses_it`, `test_commit_writes_raw_identity_and_replays_the_same_week`, `test_serial_1900_01_01_noon_is_2_5`, `test_serial_1900_02_01_15_00_is_33_625`, `test_derived_1900_03_01_is_61_not_printed_by_google`, `test_leap_year_bug_yields_62_for_derived_date`.

**Local measurement.** Append baseline, same key twice: 2 rows. Ledger: 1 row; outcomes `applied` then `replay`. Same key, different hours: `payload_conflict`, 1 row. Missing key: 0 rows. Two keys, same business fields: content-hash baseline 1 row, ledger 2 rows. The content-hash result is the wrong direction if the goal is "fewer rows," and it is the reason that baseline was rejected. Pre-coercion fingerprints of `2.50` and `2.5` match, two hashes of the same canonical record match, and a record with reversed key order hashes the same. Hashing the date stub changes the fingerprint; hashing the canonical record first still replays. The retry sleeper recorded a single 50 ms delay and then replayed, with 1 row. `RAW` keeps `00123` and keeps `=SUM(F2:F4)` as text. The USER_ENTERED stub turns `00123` into the number `123` and the formula text into a formula marker. The week commit stores `2026-10-05` as RAW text, not as a serial. Printed serial examples: `2.5` and `33.625`. Derived 1900-03-01 is `61`, and the step from 1900-02-28 is `1`. The leap-year control returns `62` for that derived date and still returns the two printed examples unchanged. `61` is not a number copied from Google. No Sheets response was observed.

**Limitation.** The ledger does not help when two real events share one id. It does not detect a different id writing a stale row version (that is the version check below). It does not make a single undifferentiated USER_ENTERED string list safe. Key expiry from the draft was not implemented: the draft leaves the policy to the resource, and this offline lab has no purge clock. The stub is not a measurement of the Sheets UI.

## 5. Validate-then-apply, script lock, and the deployment boundary

**Sources.**

- `sheets-spreadsheets-batchupdate`. https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets/batchUpdate. Method description.
- `apps-script-lock`. https://developers.google.com/apps-script/reference/lock/lock. Class description, ticket-number example, `tryLock`, `waitLock`, `releaseLock`.
- `apps-script-quotas`. https://developers.google.com/apps-script/guides/services/quotas. Current quotas and current limitations.
- `apps-script-installable-triggers`. https://developers.google.com/apps-script/guides/triggers/installable. Restrictions, time-driven triggers, errors in triggers.

**Published claim.** `spreadsheets.batchUpdate` validates each request before applying it. If any request is invalid, nothing is applied. Requests that do apply are applied together atomically. The same paragraph says collaborator changes may still alter the sheet relative to the write. The archived page used here does not define an ETag or `If-Match`.

Class Lock is mutual exclusion so one script instance runs a section at a time. The ticket example says that without the lock two form submits can read the same counter and store the same next number. `tryLock` returns false on timeout. `waitLock` throws. Spreadsheet changes should be flushed before the lock is released, or pending writes are not committed while the caller still has exclusive access.

The quotas page says quotas differ for consumer and Workspace accounts, are per user, reset 24 hours after the first request, and are subject to elimination, reduction, or change at any time, without notice. The archived table lists script runtime as 6 min / execution for both classes, triggers' total runtime as 90 min / day versus 6 hr / day, triggers as 20 per user per script, properties value size as 9 KB, and properties storage as 500 KB.

Installable triggers do not run because a script execution or API request happened. They always run as the account that created them. A clock trigger's time might be slightly randomized. A failed trigger shows no error on screen.

**Adaptation.** One week commit is one request list. Validation failure leaves the committed sheet empty. Staged cells become visible together at flush. `row_version` starts from the caller's read; a second plan that still carries the old version gets `stale_version` and writes nothing. That version is a **local stand-in** for the collaborator sentence. It is not an HTTP conditional request. A held `LockStub` makes `try_lock` return false and the apply function return `not_acquired`. `wait_lock` raises. Discarding pending cells without flush leaves the committed sheet unchanged. The Apps Script example uses `getScriptLock`, `tryLock`, no write when that returns false, a re-read of the operation-id column after the lock is held, the plain-text format `@` on the id, date, desk, and fingerprint columns before `setValues` (SpreadsheetApp has no `RAW` option), and `SpreadsheetApp.flush` before `releaseLock`. The test checks that order in the text; the script is not executed. It does not use Script Properties, because of the 9 KB / 500 KB limits, and it does not install a trigger. `DEPLOYMENT_BOUNDARY.md` transcribes the sentences above. The test asserts the text. It does not assert remaining quota or that a trigger fired.

**Code.** `src/sessionfee/plan.py`, `src/sessionfee/lockstub.py`, `src/sessionfee/commit.py`, `gas/Code.gs`, `DEPLOYMENT_BOUNDARY.md`.

**Tests.** `test_invalid_plus_valid_plan_mutates_nothing`, `test_separate_writes_baseline_keeps_valid_write`, `test_staged_batch_is_invisible_until_flush`, `test_injected_fault_rolls_back_before_any_pending_write`, `test_collaborator_edit_survives_atomic_apply`, `test_stale_version_second_plan_writes_nothing`, `test_held_lock_does_not_apply`, `test_lock_flush_is_recorded_before_release`, `test_lock_flush_commits_pending_cells_before_release`, `test_wait_lock_raises_when_held`, `test_discard_without_flush_leaves_committed_cells_unchanged`, `test_held_lock_leaves_the_week_ledger_unchanged`, `test_stale_reader_does_not_append_a_different_operation`, `test_boundary_document_contains_quota_and_trigger_sentences`, `test_apps_script_example_try_lock_flush_before_release`, `test_representative_run_opens_no_socket`, `test_dry_run_does_not_mutate_and_logs_the_outcome`, `test_zero_hours_commit_when_the_literal_total_is_zero`, `test_negative_hours_are_a_schema_reject`, `test_empty_week_writes_nothing`.

**Local measurement.** Mixed invalid-plus-valid plan: batch committed cells 0, separate-write baseline committed cells 1. After a successful flush, a collaborator overwrite of the desk cell remains `DESK-EAST` while the sibling numeric cell remains. Atomicity did not roll the later edit back. Two plans that both read version 7: the first applies, the final version is 8, the second outcome is `stale_version`, and the late cell is absent. A held lock returns `not_acquired` and does not record a flush. A successful lock records `try_lock`, then `flush`, then `release`. A cell staged while the lock is held is committed by `flush(sheet)` before `release`. The boundary file contains the without-notice sentence, both 6 min / execution cells, 90 min / day, 6 hr / day, 20 per user per script, the creator-account sentence, the API-requests sentence, the randomized-time sentence, and the no-on-screen-error sentence. The representative run, including `run_controls()` and a dry-run commit, was executed with socket connect and DNS resolution patched to fail; no call hit those patches. That is evidence this process did not open a socket on that path. It is not evidence about quota headroom or trigger latency.

**Limitation.** The batch model stops a half-applied request list. It does not freeze the sheet against a later editor. The lock stub coordinates one script's critical section in-process. It does not run in Apps Script here, and it does not stop a human editor who never takes the lock. Trigger installation and quota consumption are outside the tested surface on purpose.

## Ideas considered and not adopted

- **Header and label inference** (Chambers and Erwig, Section 6.2). Their header step was correct in 30 of 40 layouts, and the three false positives they report came from label analysis. This package already has a declared schema. Revisit only if a later version must inspect third-party workbooks with no column schema.
- **Keyless replace treated as naturally idempotent.** The draft, attributing the classification to RFC 9110, says POST and PATCH are not idempotent. An append or a second status change is a new effect unless a stored key says it is a retry. The archived RFC 9110 extract available for this work does not itself contain the idempotent-methods section, so this rejection rests on the draft's attribution, not on a reading of that RFC section. Revisit only for a full snapshot write where a repeat means "make the sheet equal this snapshot" and there is no second writer.
- **HTTP conditional requests (`If-Match`).** Not implemented. The batchUpdate page that was read does not define a validator, and the RFC extract does not contain the conditional-request section. `row_version` stays a local counter.
- **JSON Schema format assertions.** The 2020-12 validation draft was not in the readable archive. Row checks are ordinary Python predicates.
- **Hermans placement metrics as a layout optimizer.** Their placement correlations were weaker than the complexity correlations, and this lab does not move cells around to chase them.
- **A general dimension-validity predicate** for exotic products such as JPY squared. The paper treats that predicate as a separate, pragmatic list. The local measurement shows JPY times JPY is accepted. Adding a ban would be a new policy, not something their factor rule requires.
- **Idempotency-key expiry.** The draft leaves expiry to the resource. This lab has no purge clock that would change a tested result.
- **Installing a trigger or storing the ledger in Script Properties.** The quotas page limits a property value and the store, and the triggers page says script executions and API requests do not run triggers. The ledger is a sheet column in the example, and the tests do not install anything.
- **Strong typing on every formula cell a person edits.** Panko's Section 5 warning is why the extra annotations sit on the declared Python schema and the fixtures, not on a user-authored formula grid.
