# Research application

Ten public sources shape this lab. Each technique below is implemented in `src/plot_allotment` and locked by `tests/`. The registrar, the export worker, and the webhook sender are in-process. They do not call a live endpoint. The HMAC key is a synthetic 32-byte string held in code. Example JSON does not contain a `whsec_` value.

## Empty token ends the list, and the cursor is opaque

Source: AIP-158, "Pagination", https://google.aip.dev/158

`Service._list` accepts only `page_size`, `page_token`, `filter`, and `order`. `offset` and `skip` are 400, which `test_offset_query_is_rejected` and `test_skip_query_is_rejected` lock. Omitted or zero `page_size` becomes 50. A negative value is 400. `100000` is coerced to 1000, and the first page of 1001 extra rows has length 1000 plus a next token. A later call may change `page_size`. The token is a 32-character URL-safe id. The row in `page_tokens` holds the snapshot id, the cursor, the bound, the caller, the parent, the filter fingerprint, the order, and `expires_at` of three days. The token string does not contain the snapshot id. A token used with another filter is 400. An expired token is 400. Another caller's token is 403 and returns no page body. `next_page_token` is the empty string only when the snapshot has no further row. `test_short_page_is_not_the_end_when_the_server_withholds_it` shows a full first page that still carries a token. `test_empty_page_with_a_token_is_followed` follows an empty page that still carries a token. Both stop only on the empty token.

## Keyset order matches the sort, and offset shifts

Source: Sequin, "Keyset cursors, not offsets, for Postgres pagination" (2024), https://blog.sequinstream.com/keyset-cursors-not-offsets-for-postgres-pagination/

`snapshot_page` keeps rows with `(sort_key, resource_id)` greater than the cursor and less than or equal to the bound captured when the snapshot opened, ordered by `sort_key`, `resource_id`. That is the same compound order the copy used. `test_offset_misses_the_shifted_row_and_the_snapshot_keeps_it` deletes the first row of page 1 before page 2. The offset walk omits the shifted row. The snapshot walk returns it. `walks.offset_slice` counts every discarded prefix row. `walks.keyset_slice` seeks with `bisect` and counts the page length. On 5000 sorted keys, offset 1000 and limit 20 examine 1020 rows, and the keyset page examines 20. Those counts are the cost model in `test_keyset_seek_does_not_walk_the_offset_prefix`. They are not a database timing, and the lab does not copy Sequin's published timings.

## A page walk copies rows because it is many requests

Source: Atul Adya, "Generalized Isolation Level Definitions", IEEE ICDE 2000, https://www.cs.cmu.edu/~15721-f24/papers/Generalized_Isolation_Levels_Definitions.pdf

A list walk is one request per page, so a phantom can appear between pages. `copy_snapshot` inserts the matching source rows into `snapshot_rows` when the first page opens and stores the last key as the bound. `test_snapshot_ignores_a_mid_walk_insert_and_a_bumped_key` commits a new key between the cursor and the bound and bumps a sort key already read. The rest of the snapshot walk gains neither the new row nor a second copy of the bumped row. `test_live_keyset_misses_a_late_earlier_key` reads `source_rows` with no snapshot, misses a row that commits late with an earlier key, and emits the bumped row twice. That test wraps the live-walk equality check in `assertRaises(AssertionError)`, so a future change that treats the live walk as equal to the final table fails the suite. The lab uses one snapshot id for one walk. It does not implement Adya's snapshot-isolation definition, and the archived extract is not treated as that proof.

## Quoted key, fingerprint, and three stored outcomes

Source: draft-ietf-httpapi-idempotency-key-header-07, "The Idempotency-Key HTTP Header Field", https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/

The draft expired on 18 April 2026 and is not an RFC. `parse_idempotency_key` requires a quoted lowercase UUID and runs before `prepare_idempotency`. A missing header and an unquoted or non-UUID value are 400, and `idempotency_lookups` stays unchanged. The fingerprint is SHA-256 of `POST`, the upsert path including the parent, and canonical JSON with sorted keys and no insignificant whitespace. The idempotency header and the authorization header are outside that hash. Lookup is `(caller_id, idem_key)`. A miss inserts `in_progress` under the primary key. The same fingerprint while `in_progress` is 409, the journal records `idempotency_409` / `retry_without_changes`, and the 409 is not stored. A completed row with the same fingerprint returns the stored status and body. Any state with a different fingerprint is 422, recorded as `fingerprint_422` / `stop_payload_mismatch`, and the ledger row is unchanged. `test_in_progress_returns_409_and_that_409_is_not_stored` holds the first request between the claim and the finish step. The concurrent call receives 409, then the stored success, and the idempotency row never keeps status 409. Another caller with the same key string receives its own body. If the handler transaction rolls back, `release_claim` deletes the `in_progress` row and the response is 500. `test_rolled_back_handler_releases_the_claim_and_the_retry_executes_once` shows the client's retry with the same key executing once, with no 409.

## request_id stays off the resource, and retention is finite

Source: AIP-155, "Request identification", https://google.aip.dev/155

`resource_body` accepts `request_id` on the upsert, checks that it is a lowercase UUID, and drops it before the fingerprint and the ledger write. `ledger_columns()`, which reads the ledger schema, shows `request_id` is absent. `IDEMPOTENCY_TTL_SECONDS` is 24 hours. A call one second before expiry replays. At expiry the journal records `idempotency_expired` / `execute_again` and the handler runs. `prune_idempotency_body` clears the stored success body while the resource remains. The next call with that key returns the current resource and sets `x-idempotency-replay: current-resource`. A stored replay uses `x-idempotency-replay: stored`. The page-replay key is `uuid5` of the authenticated caller, the snapshot id, the resource id, and `source_version`, so the key is still a valid quoted UUID. The export worker runs the same prepare/finish steps inside its own transaction instead of calling the HTTP route.

## Each request stands alone, and If-Match is the tag this server issued

Source: RFC 9110, "HTTP Semantics", https://www.rfc-editor.org/rfc/rfc9110

The composite idempotency key uses the bearer caller label, which matches `[A-Za-z0-9._-]{1,64}`. It does not use the connection, because each request is a separate message. `finish_idempotency` runs only after `prepare_idempotency`. A completed record returns the stored success even when `If-Match` on the retry is stale, and the execution count stays 1. A new key whose `If-Match` differs from the current strong tag `"e-NNNN"` is 412. The `in_progress` row is deleted in that same transaction, the journal records `precondition_412` / `stop_not_a_replay`, and the same key can then succeed with the corrected tag and the same body. A weak `W/` value is 400 in `_upsert` before the lookup, which `test_weak_if_match_is_rejected_before_the_idempotency_lookup` locks. Comparison is exact equality of the quoted tag this server issued. `Retry-After` delta-seconds, including a decimal, replace the backoff entirely. `test_retry_after_is_not_added_to_the_cap_and_422_is_once` shows `Retry-After: 2` advancing the injected clock by 2.0. An HTTP-date is left unparsed. `test_http_date_retry_after_falls_back_to_full_jitter` shows that response waiting inside the 2 second cap and logging `full_jitter_retry`.

## The checkpoint is the barrier, and the in-flight page is replayed

Source: Paris Carbone, Gyula Fóra, Stephan Ewen, Seif Haridi, and Kostas Tzoumas, "Lightweight Asynchronous Snapshots for Distributed Dataflows", arXiv:1506.08603, https://arxiv.org/abs/1506.08603

`ExportWorker.run` is an acyclic loop: list one page, upsert its rows, then advance the checkpoint. The checkpoint stores `scope`, `consumed_token`, `param_fingerprint`, `snapshot_id`, `lease_owner`, and `lease_until`. The lab adds `next_token`, `applied_token`, `apply_ahead`, and `done`. `consumed_token` is the token that fetched the page just committed. The page body is not written into the checkpoint. `apply_atomic` puts the upserts and the barrier in one transaction. A one-shot `fail_next_checkpoint` fires after the upserts and before the barrier update, so the upserts roll back with it (`test_atomic_checkpoint_error_rolls_the_page_back`). `apply_split` commits the upserts, sets `apply_ahead`, and `write_barrier` can then raise `CheckpointIOError`. The worker logs `checkpoint_io` / `surface_error` and re-raises. Restart sees `apply_ahead`, logs `gap_detected` / `replay_uncheckpointed_page`, and replays that page. The first page was fetched with an empty token. Repeating that public call would open a new snapshot, so `_fetch_gap` calls `read_snapshot_page` on the stored snapshot id. A later page re-fetches the opaque `applied_token` through `GET`. The natural replay key and the ledger primary key leave one execution per resource id. `test_split_gap_replays_one_page_and_checkpoint_error_is_visible`, `test_split_gap_on_a_later_page_refetches_the_applied_token`, and the CLI crash-then-resume cover this. The CLI reports `duplicate_executions`, which counts resources with more than one completed idempotency record. A replay under a new snapshot would push it above 0, and `test_duplicate_metric_sees_a_second_snapshot_execution` checks that. A kill after the barrier, `test_checkpoint_then_resume_does_not_reexecute_earlier_rows`, leaves the execution count at 1. The lease is a compare-and-swap on `lease_owner` and `lease_until`, renewed before each page. Every barrier write is fenced with `lease_owner = ?`, so a worker whose lease expired and was taken over cannot advance the scope (`test_expired_lease_fences_the_old_owner`). The loser at acquisition logs `lease_denied` / `exit_without_writes`. The lease is not part of the paper. The lab does not report that paper's Flink throughput figures. Same-transaction commit closes the gap. Split mode keeps the gap testable.

## Log the fault and the decision, and let the error surface

Source: Ding Yuan, Yu Luo, Xin Zhuang, Guilherme Renna Rodrigues, Xu Zhao, Yongle Zhang, Pranay U. Jain, and Michael Stumm, "Simple Testing Can Prevent Most Critical Failures", OSDI 2014, https://www.usenix.org/conference/osdi14/technical-sessions/presentation/yuan

`Journal.record` rejects an empty fault or an empty decision. Recovery branches in the suite are `timeout_after_commit` / `replay_stored_body` when the response is dropped after commit, `idempotency_409` / `retry_without_changes`, `precondition_412` / `stop_not_a_replay`, `fingerprint_422` / `stop_payload_mismatch`, and `checkpoint_io` / `surface_error`. The checkpoint handler logs and then raises `CheckpointIOError`. There is no empty `except` on that path. The tests assert `journal.has` for each pair. A rolled-back upsert handler records `handler_error` / `release_claim` instead of leaving a claim that would answer 409 until the TTL. The CLI maps that raised error to exit 3 when `--crash-before-checkpoint` is set, and the default demo catches it once and resumes in-process.

## Sign the raw body, and acknowledge only after commit

Source: Standard Webhooks 1.0.0, https://github.com/standard-webhooks/standard-webhooks/blob/main/spec/standard-webhooks.md

`verify` checks `webhook-id`, a dot, the timestamp text, a dot, and the raw body with HMAC-SHA256. The key is the raw 32-byte lab secret. `encode_whsec` adds the `whsec_` prefix and accepts 24 to 64 bytes. A dot in the id or the timestamp fails before `hmac.new`. The signature header is space-separated. Only a `v1` tag can succeed, so `v1a` does not. The first matching secret wins, which is the rotation overlap `sign_rotation` builds. `test_whsec_round_trip_and_rotation` sends a header with a `v1a` entry, a signature from a retired key, and one from a held key, and it is accepted. A header with only `v1a` is 401. `test_whitespace_and_reserialization_fail_verification` flips one whitespace byte and also re-serializes the parsed JSON. Both fail, and the inbox stays empty. Timestamps more than 300 seconds from the injected clock fail. Bodies larger than 20 KiB are 413 before the MAC, including a body with a garbage signature. The inbox insert and `upsert_ledger_direct` share one transaction. 204 is returned after commit. A duplicate id is 204 and adds no second execution. `fail_webhook_commit` rolls the transaction back, returns 500, leaves no inbox row, and clears the execution buffer. The sender keeps the same `webhook-id`, mints a new timestamp, and re-signs. The retry then applies once. `test_sender_retry_reaches_the_receiver_with_a_stable_id` wires the sender to the receiver and checks the stable id, the fresh timestamp, the 1 second ladder wait, and a single execution.

The sender's schedule is `SHORT_LADDER_SECONDS`: immediate, 1 second, 5 seconds, 30 seconds, 2 minutes. `SPEC_LADDER_SECONDS` is the specification table whose last attempt is at 75:35:05 (`SPEC_LADDER_LAST_SECONDS`). The sender does not wait that table. Ordinary failures take the next shortened slot. Statuses 429, 502, 503, and 504 use full jitter unless `Retry-After` delta-seconds is present, in which case that value is the whole wait. 2xx stops the sender, which is why the receiver waits for commit. 3xx stores `Location`, sets `followed_redirect` false, and the next attempt uses the original URL. 410 sets `endpoint.disabled` and stops. 422 is one attempt. `INBOX_RETENTION_SECONDS` is 4 days. `test_skew_dot_duplicate_and_commit_failure` keeps the id when `prune_inbox` is called at 75:35:05 and drops it at the retention horizon. The sender advances `ManualClock` and records the waits. The tests do not wall-sleep the ladder.

## Full jitter on a private generator, judged by a local re-run

Source: Marc Brooker, "Exponential Backoff and Jitter" (4 March 2015), https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/

The client delay is `random.Random.uniform(0, min(cap, base * 2^attempt))` with base 0.05 seconds, cap 2 seconds, and the exponent capped at 62. Equal jitter is half the exponential value plus `uniform(0, half)`. Decorrelated jitter is `min(cap, uniform(base, previous * 3))`. `test_full_jitter_stays_inside_the_cap` draws attempt indexes through 80 and keeps every sample inside `[0, cap]`. The client uses a `random.Random` passed into `ExportClient` and `RetryPolicy`. It does not draw from the global `random` module.

`occsim.py` is a Python 3 port of the one-row OCC simulator: one version, read-modify-write clients, and a normal network delay. Heap entries are `(time, sequence, handler, reply_to, payload)`. The sequence number is the tie-break, so equal timestamps do not compare bound methods under Python 3. `compare_occ` reseeds `Random(seed)` for each algorithm. `test_occ_full_jitter_writes_less_than_no_backoff` calls `compare_occ(clients=12, trials=8, seed=20261006)` and asserts that the full-jitter write count on that run is lower than no backoff, and that no-backoff, exponential, equal jitter, and full jitter are all positive. Decorrelated jitter is computed in the same call. The blog's unpublished totals are not embedded. The inequality is the result of this process.
